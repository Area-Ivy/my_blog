如果你尝试用 Vibe Coding 搭建一个 RAG 系统，你会发现它的效果就是依托勾石，大概率会遇到以下几个痛点：

1. **死板的关键词匹配**：传统的向量或稀疏检索常常无法理解同义词和深层语义关联。
2. **“斩首式”的文档切分**：按照固定长度（Chunk Size）切分文档，经常把一个完整的概念强行劈成两半，导致上下文严重丢失。
3. **跨语言检索的无力感**：用户的中文 Query 很难精准匹配到前沿的英文学术文献。
4. **精度与召回率的跷跷板**：单一的检索方式很难兼顾“找得准”和“找得全”。

为了解决这些问题，我们重构了整个 RAG 链路。接下来，我将带你拆解 ResearchGO 的三层核心架构设计。

项目链接：https://github.com/Area-Ivy/ResearchGO
------

## 一、 系统架构

我们并没有采用简单的单链路结构，而是设计了一个包含**文档处理、混合检索、智能生成**的三层架构。

```
┌─────────────────────────────────────────────────────────────┐
│                    高精度 RAG 系统架构                         │
├─────────────────────────────────────────────────────────────┤
│ ┌──────────────────────────────────────────────────────┐    │
│ │          1. 文档处理层 (Indexing Layer)                │    │
│ │  PDF → 文本提取 → LLM结构化解析 → 递归语义切分             │    │
│ │  → 双索引存储 (Milvus + BM25)                          │    │
│ └──────────────────────────────────────────────────────┘    │
│                                                             │
│ ┌──────────────────────────────────────────────────────┐    │
│ │          2. 检索层 (Retrieval Layer)                  │    │
│ │  查询翻译 → Dense检索 → Sparse检索 → RRF融合             │    │
│ │  → Cross-Encoder重排序                                │    │
│ └──────────────────────────────────────────────────────┘    │
│                                                             │
│ ┌──────────────────────────────────────────────────────┐    │
│ │          3. 生成层 (Generation Layer)                 │    │
│ │  上下文构建 → LLM生成 → 答案+引用                        │    │
│ └──────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

**我们的核心技术栈选型如下：**

- **向量数据库**：Milvus
- **Embedding 模型**：OpenAI `text-embedding-3-small`
- **稀疏检索**：BM25 (`rank-bm25`)
- **重排序模型**：`BGE-Reranker-Base`
- **LLM**：GPT-4o

------

## 二、 文档处理

数据质量决定了 RAG 的上限。传统固定长度切分的弊端在于会破坏章节结构。为此，我们引入了 **LLM 结构化解析 + 递归语义切分**的方案。

### 第一步：让 LLM 帮我们读 PDF

提取 PDF 文本后，我们并没有直接切分，而是**先用 GPT-4 提取论文的树状结构**。通过 Prompt 工程，我们将整篇文档转化为包含元信息（标题、作者、摘要）和层级关系（如 `Methods > Model Architecture`）的 JSON。

### 第二步：带有层级信息的递归切分

在掌握了文档结构后，我们再进行切分。切分策略遵循严格的自然语言边界优先级：

```
段落 (\n\n) -> 行 (\n) -> 句号/问号 -> 分号 -> 逗号 -> 固定长度（兜底）
```

这样一来，每个切分出来的 Chunk 都不再是孤立的文本片段，它自带了“家谱”（如属于哪个章节、层级路径是什么），这为后续的过滤和召回提供了巨大的便利。

### 第三步：双路索引写入

处理好的 Chunk 会同时存入两套系统：

1. **Milvus 稠密索引**：保存 1536 维向量，主攻“语义相似度”。
2. **BM25 稀疏索引**：通过 Jieba 分词构建倒排索引，主攻“关键词的精确匹配”。

------

## 三、 检索核心

检索层是整个系统最复杂，也是收益最大的部分。我们在这个环节做了四件事。

### 1. 跨语言翻译

用户搜“大语言模型的注意力机制是什么”，但库里全是英文的 "Attention Is All You Need"。

虽然向量化检索用的 Embedding 模型支持跨语言，但关键词检索显然不行。

我们的策略是：探测 Query 中的中文字符比例，如果超过 30%，立刻触发 GPT-4o-mini 进行翻译，将精准的英文 Query 喂给下游检索器。

### 2. 双路并发检索：Dense + Sparse

为了保证低延迟，我们使用 Python 的 `asyncio` 并行拉起两路检索。

- **Dense Search** 负责实现向量化语义检索。
- **Sparse Search (BM25)** 负责关键词检索。

### 3. RRF 合并

向量检索给的是 L2 距离，BM25 给的是频率得分，两者的分数体系完全不同，如果加权合并的话需要作复杂的归一化处理。因此，我们采用了 **RRF (Reciprocal Rank Fusion)** 算法。它完全忽略绝对分数，只看文档在各自列表中的“排名”。

其核心公式如下：
$$
RRF(d) = \sum_{i} \frac{1}{k + rank_i(d)}
$$
这个算法极其优雅且对异常值不敏感，有效避免了单一检索系统的“偏科”。

### 4. Cross-Encoder 精排

经过 RRF 融合后，我们拿到了 Top-20 的候选片段。但在实际测试中我们发现，即使是融合后的结果，有时也会把一些包含相同关键词但语境完全不同的片段排在前面。

为了解决这个问题，我们在最后一环引入了 `BGE-Reranker-Base` 进行重排序（Reranking）。要理解这一步的必要性，我们需要理清 **Bi-Encoder（双塔模型）** 和 **Cross-Encoder（交叉编码器）** 的底层架构差异。

#### Bi-Encoder 的局限：缺乏深层交互

在前面的 Dense Search 阶段，我们使用的 `text-embedding-3-small` 本质上是一个 Bi-Encoder 模型。

它的工作机制是：Query 和 Document **完全独立**地输入模型，分别被压缩成一个高维稠密向量。我们在检索时，仅仅是在计算这两个向量之间的空间距离（比如余弦相似度或 L2 距离）。

- **优势**：极度高效。文档的向量可以离线提前计算并存入 Milvus。线上检索时，只需计算一次 Query 向量，配合 ANN（近似最近邻）算法，能实现毫秒级的海量数据召回。
- **劣势**：由于 Query 和 Document 在生成向量的过程中没有发生任何信息交换，模型只能捕捉到整体的、粗粒度的语义相关性，对于复杂的逻辑介词、多重条件等细粒度特征往往无能为力。

#### Cross-Encoder：Token 级别的注意力

为了弥补精度上的缺陷，精排阶段引入的 `BGE-Reranker-Base` 采用了纯粹的 Cross-Encoder 架构。

它彻底抛弃了独立生成向量的做法，而是将 Query 和 Chunk **拼接成一个完整的序列**（结构通常为 `[CLS] Query [SEP] Document [SEP]`），直接输入到 Transformer 网络中。

- **核心逻辑**：在这个统一的序列中，借助 Transformer 强大的 Self-Attention（自注意力机制），Query 中的**每一个 Token** 都会和 Document 中的**每一个 Token** 产生深度的注意力计算。
- **结果**：模型不再输出向量供比较，而是直接输出一个 0 到 1 之间的标量分数，代表两者的真实相关性。这种细粒度的特征交叉，使其在判断文本契合度时的准确率远超 Bi-Encoder。

#### 为什么采用两段式架构？

既然 Cross-Encoder 这么准，为什么不直接用它做全库检索？

答案是**算力瓶颈**。因为 Query 每次都是动态的，Cross-Encoder 无法像 Bi-Encoder 那样做离线索引。如果知识库有 10 万个 Chunk，每次检索就必须实时跑 10 万次 Transformer 推理。对于这种 O(N) 复杂度的计算，任何系统的延迟都将是灾难性的。

因此，现代生产级 RAG 系统普遍采用这种**“漏斗式重排架构”**：

1. **初排（召回阶段）**：利用 Bi-Encoder + BM25 的极速特性，从海量文档中以毫秒级速度粗筛出 Top-20。
2. **精排（Rerank 阶段）**：利用 Cross-Encoder 的高精度特性，仅对这 20 个候选切片进行高强度的联合推理，精准挑出最相关的 Top-5 喂给大模型。

这是一种用少量的算力开销，换取检索精度大幅提升的极致性价比方案。

## 总结

搭建一个高精度的 RAG 系统，绝不仅仅是把文本变成向量存起来那么简单。从基于 LLM 的结构化解析，到并行的混合检索，再到严谨的 RRF 融合与 Cross-Encoder 重排序，每一个环节都在为最终的“准确”服务。
